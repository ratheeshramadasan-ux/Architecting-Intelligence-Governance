# 0.11 Standard deliverable schema

| Field | Requirement |
|---|---|
| ID and version | Stable and immutable identity; semantic version |
| Name and purpose | Plain-language output and business reason |
| Stage/workstream | Primary lifecycle placement |
| Type and criticality | Controlled taxonomy; mandatory, conditional or recommended |
| Owner/author/validator/approver | Named roles; accountable owner must be singular |
| Inputs and collection sources | Required information and system/person of record |
| Method and template | Creation instructions and approved format |
| Acceptance criteria | Testable completion conditions |
| Validation and evidence | Checks performed and proof retained |
| Dependencies | Required predecessor deliverables |
| Controls and architecture links | Typed traceability |
| Gate | Gate that consumes this deliverable |
| Status | planned, draft, in-review, approved, superseded or archived |
| Dates | due, approved, review and expiry |
| Classification/access | Sensitivity and permitted audiences |
| Storage and retention | System of record and retention rule |
| Exceptions | Decision, owner, expiry and compensating control |

Deliverable cards show purpose, stage, owner, status, criticality, due/review date and the next decision. A download is an attachment to a deliverable record, never the deliverable itself.
